Elevating What's Already Working

01

UI/UX Workflow — Requirements → Wireframes → Iteration

Feedback: "Strong foundation in UI/UX design workflows — clarifying requirements, wireframes, iterating with stakeholders."

You described the process well. The next level is showing what happens when the process breaks down — that turns a process answer into a judgment answer, which is what senior interviewers actually listen for.

Add one sentence about how you handle conflicting requirements or stakeholder disagreement mid-iteration. That signals you've operated in messy real conditions, not just ideal ones.

Say this next time "When stakeholder feedback contradicts user research, I frame the decision around the specific risk on the table — 'if we go this direction, we're betting that X.' Then I let the team decide with that tradeoff made explicit. It takes the argument out of taste and puts it into consequence."
02

Figma — Wireframing, Prototyping, Design Specs

Feedback: "Practical knowledge of in-file documentation, structured pages, and component variants."

You're clearly strong here. Elevate it by naming the why behind your Figma choices — not just the what. The what is table stakes. The why signals design systems thinking.

What you said "I use component variants and structured pages for handoff."
What lands harder "I name every component state explicitly — default, hover, disabled, error — so engineers don't have to infer edge case behaviour. It reduces back-and-forth by 40–50% in my experience."
03

Design System Thinking — Auto-layout, Typography, Shared Libraries

Feedback: "Focus on maintaining visual consistency and responsive design across web interfaces."

Add one concrete example of a decision the system made for you — a moment where the system caught an inconsistency you would have missed, or where a constraint in the system guided you toward a better solution. That's the difference between someone who uses a design system and someone who thinks in systems.

Example angle "One moment that stood out — a new component I was designing broke the 4px grid I'd established in the shared library. The system flagged it before it reached developers. That's when I realised the library wasn't just documentation, it was a QA layer."

Gap 01 — Close This

UX Artifacts, KPIs & Research Methods

—

Personas — Stop Describing Demographics, Start Describing the Tension

Feedback: "Could have provided more detailed explanations about artifacts like personas and user journeys."

Interviewers don't want a demographic profile. They want to hear the goal-frustration pair — what the user is trying to accomplish, and what specifically prevents them from doing it today. That's where the design work lives.

Weak persona answer "We created personas based on age, occupation, and tech comfort. Our primary user was a 28–35 year old professional."
Strong persona answer "Our primary persona was time-constrained and making decisions on mobile in under 90 seconds. That single constraint shaped every layout decision — density, tap target size, information hierarchy. Demographics didn't drive the design; the constraint did."
—

User Journeys — Frame as Emotional Arcs, Not Task Lists

A journey map that lists steps is a flowchart. What interviewers want: where does the user feel confused, frustrated, or relieved? That's where design decisions live — not in the steps, but in the emotional gaps between them.

How to describe it "In the journey map, the biggest drop in confidence happened right after signup — users had committed but didn't know what to do next. That moment of uncertainty became the design problem we focused on. Everything else was secondary."
—

KPIs — Connect Design Decisions to Specific Metrics

Feedback: "Tying KPIs directly to business goals, referencing additional research and analytics methods."

Every design decision has a measurable proxy. Learn these pairings and use them fluently:

  • →Onboarding redesign → Activation rate (% of users who complete the first key action)
  • →Navigation restructure → Task completion rate + time-on-task
  • →Visual consistency work → NPS + qualitative sentiment in user interviews
  • →Reducing friction → Drop-off rate at specific funnel steps
  • →Feature discoverability → Feature adoption rate over 30/60/90 days
If you don't have real metrics from client work Use hypothetical ones framed as what you'd measure: "We didn't have instrumentation on that project, but the metric I'd have tracked is task completion rate on mobile — because that was the behaviour the redesign was specifically trying to change."

Gap 02 — Close This

Figma Handoff Specifics

—

Tokens, Measurements, Responsive Rules, Interaction Notes

Feedback: "Could have benefited from explicitly mentioning specific spec conventions — tokens, measurements, responsive rules, and interaction notes — along with a detailed handoff checklist."

The interviewer wanted to hear that your handoff is systematic, not ad-hoc. Here's the full vocabulary to use, and what each term means in practice:

  • TTokens — Named values for spacing, colour, typography, and border radius. Instead of a raw 16px, it's --spacing-4 or --color-forge. Engineers reference the token; the token can be changed globally without touching every component.
  • ⬡Measurements — Document min and max widths, not just fixed values. State which measurements are responsive and which are fixed. If a card is min-width 240px and max-width 360px, that needs to be explicit.
  • ↔Responsive rules — Specify breakpoints (375, 768, 1280, 1440) and show how components reflow at each. Don't leave this to engineering interpretation.
  • ↻Interaction notes — Any non-obvious interaction (hover, transition duration, easing curve, trigger delay) gets a written annotation in the Figma frame, not just a prototype link.
The handoff answer that lands "My handoff includes: named components with all states documented, a token reference sheet, per-breakpoint layout specs, motion notes for every animated element, and a one-page interaction summary for anything with conditional logic. I also do a 30-minute walkthrough with the lead engineer before dev starts — that single meeting catches 80% of edge-case questions before they become Slack interruptions."

Visual Specs, Motion & Anchor Positioning

—

Spacing Tokens, Width Limits, Viewport Edge Behaviour

Feedback: "Needed clearer and more concrete specs on spacing tokens, width limits, and viewport edge behavior."

Use and explain the 4px base grid. All spacing — padding, margin, gap — should be multiples of 4. This aligns to most device pixel ratios and creates natural visual rhythm that's easy to scale. When interviewers hear you say "4px grid," they know you've thought about consistency at a system level, not just visual taste.

  • →Fixed vs. fluid widths — Know the difference and state it. "This container is max-width 1200px, centred with auto margins, with 48px horizontal padding at desktop collapsing to 24px at mobile."
  • →Viewport edge behaviour — Content should never touch the viewport edge without intent. State your minimum edge margin explicitly. "I set a minimum 20px safe zone on all sides at every breakpoint."
  • →Width limits on text — Long-form text should have a max-width of around 65–75 characters per line (roughly 640–720px) for readability. State this in your specs.
—

Anchor-Based Positioning & Collision Handling

Feedback: "More detail on anchor-based positioning and collision handling."

Anchor-based positioning applies to any element that positions itself relative to a trigger — tooltips, dropdowns, popovers, context menus. Here's exactly what to spec and say:

  • 1Primary anchor point — Where does the element prefer to appear? (e.g. below-left of the trigger button)
  • 2Fallback positions in priority order — If below-left overflows, try below-right, then above-left, then above-right.
  • 3Flip threshold — How close to the viewport edge before the position flips? (e.g. 12px minimum clearance before flip triggers)
Say this next time "For any anchored UI — tooltips, dropdowns — I specify the primary anchor point, fallback positions in priority order, and the minimum viewport clearance before a flip triggers. Without that, engineers make inconsistent choices at edge cases, and the result looks broken on small viewports or near screen edges."
—

Motion Specs & 3D / Interactive Animation

Feedback: "Elaborate more on motion and 3D/interactive animation scenarios."

Motion has four properties. Specify all four for every animated element — this is what separates a designer who thinks about motion from one who prototypes it and hopes for the best:

  • ↑Duration — In milliseconds. Micro-interactions: 100–200ms. Page transitions: 250–400ms. Never leave this unspecified.
  • ~Easing curve — ease-out for elements entering the screen (fast start, slow finish — feels natural). ease-in for elements leaving (slow start, fast finish). ease-in-out for repositioning. Never use linear for UI motion — it looks mechanical.
  • ⏱Delay — Intentional delay for staggered lists or sequential reveals. Always document if non-zero.
  • ↻Trigger — Scroll, hover, load, click, or state change. The trigger must be documented alongside the animation.

For 3D and interactive animation specifically: specify the axis of rotation or translation (X, Y, Z), the transform origin (where in the element the transformation radiates from), and whether the animation responds to user input (mouse position, scroll progress) or runs automatically.

Always add this line "I document whether the motion respects prefers-reduced-motion — and what the static fallback is. Motion should never be required to understand the UI."
Meta Fix — The Root Cause

The One Habit That Closes All Three Gaps

Every weak point in the feedback shares the same root cause: you described what you do without describing why you do it and what the exact output looks like. The process was there. The artifact — the concrete, specific, tangible thing that came out of that process — was missing.

Next interview, for every process answer, finish the sentence with: "…and the concrete output of that is [specific artifact, deliverable, or metric]." One habit. Closes all three gaps simultaneously.

Instead of: "I run user research at the start of every project."

Say: "I run user research at the start of every project — the concrete output is a two-page problem definition document that specifies the exact user action we're designing for, the friction causing the drop-off, and the metric we'll use to know the design worked. That doc is what every subsequent decision gets checked against."
